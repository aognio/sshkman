# Zero-Knowledge Threat Model and Envelope Encryption Format

* Status: accepted
* Date: 2026-11-04
* Deciders: Principal Engineer & Security Architect
* Scope: Cryptographic Envelope, Zero-Knowledge Boundary, Wire Format

## Context and Problem Statement

The system must guarantee zero knowledge with respect to SSH private keys, vault passwords, and sensitive metadata (slugs, hostnames, usernames, SSH options). The server must never receive or be able to derive these plaintext values.

We need a standardized, versioned envelope format that supports:
1. Client-side key derivation from master password.
2. Independent recovery key wrapping without server access.
3. Fast re-wrapping of the Vault Master Key (VMK) during password rotation without re-encrypting all identity records.
4. Tamper-evident authenticated encryption with context-bound associated data (AAD).

## Decision Drivers

* Strict zero-knowledge: server receives only ciphertext and public KDF parameters.
* Modern cryptographic primitives: Argon2id (RFC 9106) and XChaCha20-Poly1305 (RFC 8439 / extended 192-bit nonce).
* Defense against cross-record, cross-vault, or cross-user substitution attacks.
* Explicit rejection of `age` password mode due to `age`'s scrypt dependence.

## Considered Options

* Option 1: `age` crate password encryption (Rejected: age uses scrypt, violating Argon2id mandate).
* Option 2: Custom AES-CBC + HMAC scheme (Rejected: vulnerable to padding oracles, manual primitives).
* Option 3: Audited Argon2id + XChaCha20-Poly1305 with AEAD Context-Bound Envelopes.

## Decision Outcome

Chosen option: Option 3 ("Argon2id + XChaCha20-Poly1305 Envelopes").

### 1. Key Hierarchy
1. **VMK (Vault Master Key)**: 256-bit random key generated by client CSPRNG (`OsRng`).
2. **KEK (Key Encryption Key)**: Derived from vault password via Argon2id:
   - Algorithm: `Argon2id`
   - Version: `0x13`
   - Memory cost: `19456` KiB (configurable up to `65536`)
   - Time cost: `2` iterations
   - Parallelism: `1`
   - Salt: 16-byte random CSPRNG
3. **Wrapped VMK**:
   - Cipher: `XChaCha20-Poly1305`
   - Nonce: 24-byte random CSPRNG
   - AAD: `sshkma:vmk:v1:<user_id>`
   - Payload: 32 bytes VMK
4. **Recovery Wrapped VMK**:
   - Secondary wrapping of the identical VMK using a 256-bit high-entropy recovery secret.
   - AAD: `sshkma:recovery:v1:<user_id>`

### 2. Identity Record Encryption
Each identity envelope encrypts the complete identity record:
```rust
pub struct PlaintextIdentityRecord {
    pub slug: String,
    pub host_alias: String,
    pub hostname: Option<String>,
    pub user: Option<String>,
    pub port: Option<u16>,
    pub private_key_openssh: String, // original verbatim bytes
    pub public_key_openssh: String,  // original verbatim bytes
    pub extra_ssh_directives: Vec<(String, String)>,
    pub created_at: u64,
    pub updated_at: u64,
}
```
- Cipher: `XChaCha20-Poly1305`
- Record Key: Derived via `HKDF-SHA256(ikm = VMK, salt = user_id, info = "sshkma:record:" + identity_id)`
- Nonce: 24-byte random CSPRNG
- AAD: `sshkma:record:v1:<user_id>:<identity_id>`
- Wire format:
  `[magic: 4B = "SKM1"] [nonce: 24B] [ciphertext + 16B poly1305 tag]`

### Positive Consequences

* Changing master password re-wraps only the 32-byte VMK; identities do not need re-encryption.
* Context-bound AAD prevents moving a ciphertext envelope to another identity or user.
* Server administrator cannot read identity slugs or hostnames.

### Negative Consequences

* Record size and count remain observable to server host.
